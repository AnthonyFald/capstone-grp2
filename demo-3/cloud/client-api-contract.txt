EVERGREEN CLIENT SITE

The client site is served at /client/ on the Capstone Worker. Account and
project operations use /api/capstone/v1/client. The older Team 2 experiment
keeps its separate keys, board, lessons and metrics. Client signup does not
grant experiment access. The existing Capstone processing host claims client
work through the same lease protocol and returns a draft to the client site.

Accounts and projects

- POST /signup: name, email, passwordProof, role family (gc, sub, architect),
  and either a projectName or inviteCode. Only GC and Sub founders can create
  new projects. New projects have their own IDs. The invitation assigns the
  exact role within the selected family and checks the recipient email.
- POST /login: email and passwordProof. POST /logout expires the session.
- Use public/client/auth.mjs to derive the password proof in the browser.
  Submit it only to this same-origin API. Treat it as a password and keep
  it out of logs, local storage, and screenshots. The Worker stores a
  salted keyed verifier. The browser keeps a 12-hour HttpOnly session.
- CAPSTONE_CLIENT_AUTH_PEPPER is the recommended dedicated Worker secret.
  Set it before creating accounts and retain it across deployments.
  Without it the current Capstone owner secret supplies the key. Changing
  that secret or adding a pepper later will invalidate existing verifiers.
- CAPSTONE_CLIENT_SIGNUPS=closed disables new accounts. Existing accounts
  can still sign in. There is no account-recovery email service.
- POST /invites: a GC manager supplies email, subrole and optional trade for
  a subcontractor. Subroles: gc_manager, gc_supervisor, gc_employee, sub_lead,
  sub_field, architect_lead, architect_designer. Omitted subrole defaults to
  sub_lead for older clients and legacy invite codes. The one-use code binds
  email, project, trade and role. Give it only to the intended teammate.
- GET /dashboard shows the account, project, visible run history, runner
  check-in, review totals and authorized project record metadata. GC managers
  see their own runs and intentionally shared project runs. GC supervisors
  see their own runs and shared RFIs. Other accounts see their own runs.
- POST /project-records: clientRequestId (for safe retries), kind (document, task, milestone), title, details,
  visibility (project, restricted), dataClassification (synthetic, authorized)
  and scheduledFor (required for milestones, optional for tasks). A GC manager
  can publish restricted records. GC managers/supervisors can add planning
  records. GC managers/supervisors, Sub leads and both Architect roles can
  add documents. Browser file import sends the reviewed extracted text.
- GET /project-records/:id returns the full record. Project membership limits
  all reads. Only GC managers and project architects see restricted records.
  Adding a project record does not submit a model job or update a review board.

Jobs and evaluation

- POST /runs: kind, title, clientRequestId, dataClassification, payload and
  optional shared=true for project members with share permission. The request ID makes
  retries idempotent. Choose synthetic or authorized data. Every queued
  batch is sent to the project processing host during an enabled session.
- Payload for rfi is {mode:"consolidation",documents:[...]}. The document
  requirements match the experiment consolidation API. Meeting uses
  {transcript:"..."} and daily uses {reports:[...]}.
- GET /runs/:id returns status, input, draft, review, timings and a small
  provenance record. Access is checked by the Worker for every request.
- POST /runs/:id/share can retract or restore sharing on a run that
  was shared when queued. Private project history and shared history use
  separate task boards. A run generated against private history cannot be
  switched to shared.
- POST /runs/:id/review records decision (accept or revise), notes, and
  optional metrics. GC managers and Sub leads can accept or request changes
  on accessible runs. GC supervisors can request changes. Other members read
  drafts without review access. An owner accepting their RFI batch also applies its
  recommendations to their appropriate board. A GC reviewing a shared
  Sub result records a review without modifying either board. An obsolete
  board snapshot must be rerun before it can be accepted.
- Metrics can include correctFacts, incorrectFacts, missingFacts,
  extraErrors, reviewSeconds and manualSeconds. Completeness and accuracy
  use explicitly scored results. An assisted/manual time comparison needs
  generation, review and manual time for the same run. No result alone
  estimates RFI reductions.

Reviewed guidance

- POST /runs/:id/guidance with {text} saves a reusable instruction after
  the submitter reviews their own completed RFI run. Use a short rule a
  reviewer can check. Review notes and uploaded records are never copied
  into guidance. One instruction can be saved per reviewed run.
- GET /dashboard lists the signed-in account's active private and shared
  instructions. The scope follows the run selected at intake. Private
  instructions and shared-run instructions have separate versions and
  never mix. The GC cannot read a subcontractor's saved instructions.
- POST /runs with useGuidance=true opts in for a new RFI run in the
  matching scope. Up to eight active instructions of 500 characters each
  are copied into the queued job. Without that opt-in, no instructions
  go to the model.
- GET /runs/:id reports useGuidance, guidanceVersion and guidanceSnapshotId.
  The submitter can inspect the exact saved text used by that run. Other
  reviewers of a shared result only see that the run used guidance.
- POST /guidance/:id/archive removes an instruction from future runs.
  In-flight jobs and retries retain the same snapshot. This feedback loop
  supplies reviewer guidance to the existing model. To measure its
  effect, compare the same input and board with guidance on and off.

The Worker uses existing free D1, bounded account/queue capacity and no
cloud inference. The runner must be started for work to leave the queue.
Run the additive schema.sql before deploying this Worker version. Existing
accounts, sessions, jobs, and old invitation codes are preserved.
Client runs never retrieve experiment lessons or experiment board history.
The claim response advertises clientWorkflows. Current runners use
clientExtendedOnly=true when claiming meeting/daily work so old experiment
jobs remain untouched. See tests/client.test.mjs for role, queue, sharing
and evaluation examples.
